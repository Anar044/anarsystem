# Smart Horeca — Platform Admin / Организации (D1 v1)

## Решение на первый этап
- **НЕ создавать новую D1 / PLATFORM_DB**. Используется существующая Cloudflare Pages binding `DB`.
- Каждая новая организация получает отдельную запись в `sh_workspaces`, со стабильным `workspace_id` и внутренним `owner_user_id = platform-org:<uuid>`.
- Реестр платформы хранится в `sh_platform_organizations`, а операции Platform Admin — в `sh_platform_audit`.
- Статусы: `DRAFT`, `ACTIVE`, `SUSPENDED`.
- Серверные подключения и операционные данные пока остаются в общей D1, с логическим разделением по workspace/owner. Физическая изоляция PostgreSQL — отдельная будущая миграция.
- **Чистый запуск**: миграции существующих организаций и TEST CHAIN не делаем. Подключения и приглашения создаются заново из Platform Admin. Старые данные D1 не удаляются автоматически при публикации кода.

## Авторизация
- Только Supabase Auth user UUID, заданный в Cloudflare Pages переменной `PLATFORM_ADMIN_USER_IDS`, даёт доступ к `/platform-admin.html` и API `/api/platform/organizations`.
- Пример значения: `<UUID_пользователя>` или список UUID через запятую. Email НЕ подходит.
- Пустой список запрещает доступ всем. UUID узнать в Supabase Dashboard → Authentication → Users, без передачи пароля, access token, секретных API ключей или cookies.
- Отдельного адреса/домена и нового Supabase проекта не требуется.
- Нельзя доверять роли `platform_admin`, присланной клиентом.
- Организационный SYSADMIN получает обычную роль `ADMIN` (`*`) только своего Workspace; доступа к API платформы он не получает.

## Работа кабинета
1. `/platform-admin.html`: создать организацию и выбрать RMS/CHAIN. Она в статусе DRAFT.
2. Нажать «Подключить сервер» и ввести публичный хост, порт, логин и пароль SH Server. Сервер проверяет авторизацию и получает подразделения. Без корректного соединения данные не сохраняются.
3. После подключения нажать «Включить» (ACTIVE).
4. «Пригласить SysAdmin» по email; отправить ему полученную одноразовую ссылку приглашения.
5. SysAdmin подтверждает email, попадает в назначенную организацию и в её меню «Пользователи и права» приглашает сотрудников.
6. Если один Supabase пользователь имеет больше одной ACTIVE организации и нет сохранённого выбора, при входе показывается выбор организации. При обычном выходе выбор очищается.
7. Platform Admin может приостановить организацию без удаления документов, сотрудников и состояния подключения.

## Важные ограничения первой версии
- Создание организации НЕ подключает сервер автоматически: Platform Admin вручную подключает его и проверяет реальные подразделения через `POST /api/platform/server`.
- Для новых платформенных организаций сотрудники не могут сохранять/удалять серверное подключение через `/api/iiko/state`; подключение задаёт только Platform Admin через `/api/platform/server`.
- Для сохранения пароля требуется Cloudflare secret `SMART_HORECA_STATE_ENCRYPTION_KEY`; при отсутствии сохранение заблокировано. Никогда не хранить секрет в GitHub или браузерном коде.
- Адрес сервера должен быть публично доступным из Cloudflare; локальные и зарезервированные IP адреса запрещены, TLS/HTTPS напрямую текущим `iiko-client` пока не поддерживаются (подключение использует HTTP). Для безопасной боевой работы нужен защищённый шлюз и ограничение доступа.
- Выбор режима RMS/CHAIN задаётся в карточке организации, API в этой версии его не определяет автоматически.
- `/api/account/state` для новых организаций использует ключ `org-user:<workspaceId>:<userId>`, чтобы не смешивать личные QR/OLAP настройки одного пользователя между новыми организациями. Старые данные аккаунтов остаются на старых ключах.
- Публичные URL, другие старые API и все операционные таблицы требуют дополнительного аудита tenant scope **перед запуском внешних клиентов**. Одного ограничения в меню недостаточно для гарантии полной изоляции.
- Приглашение обязательно: старое автоматическое восстановление организации владельца по данным сервера и привязка по одному email отключены. Вход в организацию — только через действующее приглашение и членство.
- Отправка email самостоятельно через UI не выполняется: генерируется ссылка, которую оператор отправляет вручную.
- Не следует создавать реальные клиентские организации до полного аудита tenant-изоляции операционных API и надёжного защищённого сетевого соединения к SH Server.
- Production D1 и Supabase Auth автоматически не очищаются. Удаление данных — отдельная операция после backup и подтверждения точного перечня таблиц.

## Будущая миграция на PostgreSQL
Сохраняем неизменные `organization_id` / `workspace_id`. Создаём отдельные базы PostgreSQL для каждой организации, переносим таблицы и документы с проверкой счётчиков и журналов. D1 используется как переходное хранилище, а не как модель физической изоляции навсегда.

## Чистый старт (порядок перед публикацией)
1. Сделать резервную копию текущей D1 через Cloudflare и проверить, что копия доступна для восстановления. Экспортировать связанные файлы R2, если в них есть нужные данные.
2. Согласовать, что именно удаляется: только связи/подключения организаций или все операционные документы (закупки, HR, табели, зарплаты, накладные, QR и т. д.). Не приравнивать эти наборы данных.
3. Не удалять Supabase Auth учётную запись администратора платформы; без неё Platform Admin нельзя открыть. Сначала задать Cloudflare Pages переменную `PLATFORM_ADMIN_USER_IDS` с её UUID и проверить доступ.
4. После явного подтверждения выполнить целевой reset данных в текущей D1. Код веб-сайта и таблицы схемы можно сохранить, очистив только строки согласованного набора данных.
5. Создать первую новую организацию через Platform Admin, настроить сервер и отправить приглашение SysAdmin.
6. Проверить работу нескольких организаций на независимых пользователях, включая кросс-организационную защиту данных и смену организации.

**Никакой destructive SQL не выполняется в рамках этого PR.** Доступ к рабочей базе Cloudflare через GitHub сам по себе отсутствует.

## Provisioning SH Server (v2)
- `GET /api/platform/server?organizationId=<uuid>` показывает адрес, порт, логин, число подразделений, дату проверки и булев маркер наличия пароля; сам пароль никогда не возвращается.
- `POST /api/platform/server` принимает выбранную организацию и `{ connection:{ host, port, login, password } }`, проверяет доступность сервера и сохраняет зашифрованный state в существующей D1 по стабильному синтетическому `owner_user_id` организации.
- `DELETE /api/platform/server` удаляет подключение только у приостановленной организации.
- При неудачной проверке новый state не сохраняется, старый не затирается.
- Чтобы предотвратить незапланированную отправку секретов во внутреннюю сеть, клиент не может указать `localhost`, локальные IP, URL-схему и путь.
- Существующий endpoint получения подразделений используется повторно (с OLAP fallback при пустом ответе).
- После создания организации сначала подключить сервер, затем активировать организацию, потом пригласить SysAdmin.
