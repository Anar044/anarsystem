# Smart Horeca — QR Menu → чаевые → Payriff: этап 2

**Статус:** подготовка безопасного реестра и бухгалтерского интерфейса. Нет отправки реальных денежных переводов.

## Подтверждённая бизнес-логика

1. Гость платит одним платежом на принимающий счёт ресторана: стоимость блюд + выбранные чаевые.
2. Проверенный сервером Payriff-платёж даёт одно обязательство перед конкретным сотрудником HR (не перед столом).
3. Обязательство сохраняется в D1 до завершения выплаты, отмены по разрешённой финансовой процедуре либо разрешения спорного статуса.
4. Физическая выплата идёт со **второго** счёта ресторана. Если денег нет, обязательство продолжает жить в очереди. Бухгалтер пополняет второй счёт.
5. Один сотрудник может работать в нескольких RMS; его HR ID един, настройки видимости официанта и второго счёта ограничены рестораном.
6. Фискальная сумма продажи и чаевые должны отражаться отдельно, без двойного учёта. RRN получения денег должен поступать в кассовый плагин после подтверждения реального платежа.

## Что включено в этом этапе

- `functions/api/tips/_lib/ledger.js` — идемпотентная запись обязательств, только из будущего **доверенного серверного** обработчика фактически оплаченного QR-заказа. Никакого публичного `POST /record-tip` нет.
- `functions/api/tips/queue.js` — бухгалтерский GET журнала/очереди и POST настроек с финансовым разрешением; уникальные ключи (owner_id, restaurant_id) не позволяют смешать сети.
- `tips.html` / `tips-queue.js` — два Merchant ID, сообщаемый бухгалтером остаток, очередь. Merchant ID — лишь черновой идентификатор до проверки структуры двух счетов у Payriff; *не* API-ключ.
- Для каждой записи: QR order ID, Payriff payment ID, HR employee ID, сумма в **гяпиках (integer)**, статус, история попыток в отдельной таблице для будущей интеграции. База не хранит CVV/PAN.
- Очередь: WAITING_CARD, WAITING_PROVIDER, WAITING_BALANCE, WAITING_FUNDS, READY_FOR_PROVIDER; неизвестные провайдерные исходы блокируют новые отправки до сверки. Готовность к отправке не означает, что платёж отправлен.
- Дубликаты Payriff payment ID с теми же деталями возвращают прежнюю запись; с другим получателем или суммой отклоняются.

**Важно:** сейчас поступления с QR ещё не подключены. Реестр останется пустым, пока следующий этап не добавит подтверждённые заказы.

## Открытые вопросы Payriff (до включения переводов)

Нужен договор и реальное описание API для **пополнения карты сотрудника**, не `AutoPay`, которое списывает с сохранённой карты. Публичная `GET /api/v3/cards/save/{id}` подтверждает готовность карты для AutoPay, но сама по себе **не подтверждает возможность выплаты** на cardUuid. Публичный `POST /api/v3/payout` также может означать другие виды движения средств. Не использовать неподтверждённый API в платёжном коде.

У Payriff запросить:

1. Как идентифицировать приёмный счёт и отдельный депозит выплат; один или два Merchant ID? Как получать **подтверждённый** остаток именно второго счёта?
2. Какой конкретно API даёт перевод **на карту физического лица** из второго счёта? Какие разрешения требуются; нужные поля (PAN или token, имя, FIN и т.д.)?
3. Как привязать карту, не обрабатывая её полный номер на сайте Smart Horeca? Есть ли hosted secure onboarding и поддержка payout recipient token?
4. Поддерживаются ли idempotency key, client request RRN, запрос статуса по client reference и asynchronous callback; как обрабатывать timeout / UNKNOWN без повторного перечисления?
5. Минимальная сумма выплаты, валюта, комиссии, ограничения по картам, лимиты и доступность API в sandbox; как получать реестр и сверку платежей?
6. Нужны правила налогового и бухгалтерского учёта чаевых и возвратов, требования к согласию сотрудника и сроки хранения платёжной информации.

## Строгие правила будущего payout-worker

- Никакого снятия средств до проверки прав организации, ресторанного ID и merchant ID.
- Секреты Payriff — только на сервере в зашифрованном хранилище (ключ шифрования из окружения), не в D1 открытым текстом, не в браузере и не в GitHub.
- Полный номер карты / CVV в Smart Horeca не вводится. Если Payriff требует PAN, выбираем согласованный PCI-compliant вариант, иначе запускать нельзя.
- Таблицы `qr_tip_liabilities`, `qr_tip_payout_attempts` существуют сейчас. Воркера отправки и reconciliation по API **пока нет**.
- Перед реальной отправкой создавать durable attempt с устойчивым idempotency key. После таймаута — состояние RECONCILE и запрос в Payriff по ключу/референсу; повторно отправлять только если Payriff подтвердил, что предыдущего перевода не было. Ни при каких условиях не считать HTTP 200 фактом зачисления.
- После ошибки недостатка средств долг остаётся в очереди. Состояние PAID ставить только после окончательного подтверждения Payriff, с сохранением провайдерного ID.
- Если меняется карта после создания обязательства, новая карта должна быть подтверждена; уже выполняющийся перевод не менять задним числом.
- Возвраты/отмены — отдельный учёт и однозначная процедура, особенно если чаевые уже перечислены.
