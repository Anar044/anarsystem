# Smart Horeca QR Pay — оплата до передачи заказа в iikoFront

**Решение владельца: 30.10.2026.** Этот документ заменяет прежнее предположение «создать POS-заказ, затем оплатить на кассе» для публичных QR-заказов. Классический заказ, создаваемый официантом в iikoFront, не затрагивается.

## Непересматриваемое правило

Неподтверждённая оплата, отмена, отказ, тайм-аут, обратный редирект клиента, поддельный webhook и предавторизация (hold) **не** разрешают создавать заказ на кассе или отправлять на кухню. Подтверждение оплаты означает серверную проверку фактического успешно проведённого платежа у Payriff, включая merchantId, transaction/orderId, собственный idempotency key, валюту AZN, точную сумму и restaurant/organization scope. Нельзя доверять данным из браузера или одному callback без независимой проверки у PSP.

До оплаты допускается только **платёжный черновик** (payment intent) — снимок корзины и цены, привязанный к ресторану, столу и сроку действия. Это **не POS-заказ**, **не кухонное задание**, **не реализация**.

## Требуемая последовательность

1. Гость открывает индивидуальный QR стола; сервер проверяет table token, выбранный ресторан и публикуемое меню.
2. Сервер проверяет POS-готовность, текущие цены, блюда, стоп-листы, модификаторы; рассчитывает сумму и фиксирует неизменяемый короткоживущий payment intent.
3. Сервер создаёт оплату Payriff с точной суммой, AZN, собственным уникальным reference. На телефоне «Оплатить». Секрет PSP хранится исключительно на сервере конкретной организации.
4. Возврат на success URL / клиентский текст / webhook **не переводят** intent в PAID. Backend по секретному серверному API отдельно читает действительное состояние платёжной операции. Только завершённая успешная оплата (не PREAUTH) с совпадающими merchant, currency, amount и reference становится VERIFIED_PAID. Один provider transaction должен использоваться не более одного раза.
5. Одной атомарной операцией создаётся идемпотентное задание POS по `externalOrderId` с доказательством подтверждённой оплаты. Правильный стол, продукты, цены и идентификатор оплаты проверяются снова; касса не списывает деньги повторно.
6. После успешного создания ровно одного POS-заказа разрешается **однократная** кухонная печать с долговременным журналом PREPARED/PRINTED/CHECK_REQUIRED. Клиент видит достоверный статус.
7. Оплаченный online заказ должен быть проведён с подходящим типом оплаты / фискальным учётом в POS, без повторной оплаты наличными/картой. Схему подтверждения фискализации и финансовых проводок согласовать с кассовой интеграцией; не подставлять фиктивный RRN или номер чека.

## Ошибки и возвраты

- Ошибка до подтверждения Payriff: платежный черновик истёк или отклонён, **ничего не отправлять** на кассу.
- Списание подтверждено, но POS/принтер недоступен: сохранять обязательство перед гостем, статус «Оплата получена — заказ задерживается», сигнал сотруднику, не требовать платить второй раз, безопасный повтор с тем же externalOrderId или подтверждённый возврат.
- Нет товара/изменилась цена в момент завершения оплаты: не подменять состав заказа; инициировать согласование/возврат, корректно записать возмещение.
- Повтор webhook или обновление страницы: idempotency на платёж, intent, заказ, POS запись и печать.
- Интернет не работает: не подтверждать оплату и не создавать заказ, пока PSP не подтверждён; при подтверждённой оплате держать безопасную очередь.
- В одной Smart Horeca много организаций: merchantSecret и merchantId только для выбранной организации; сверка реального restaurant/organization scope обязательна.

## Текущее безопасное состояние

**Существующие исходники не являются завершённой онлайн-оплатой.** Пока нет Payriff payment intent + server-side settlement verification, API `guest-orders POST` возвращает `QR_ONLINE_PAYMENT_NOT_READY`, админка не позволяет включить публичный приём, полный POS hello отклоняется, POS pull и ackCreated/ackKitchen заблокированы. Расписание загрузки залов и столов, индивидуальные QR и просмотр меню остаются.

Старый `PAY_AT_POS` POS Bridge контракт должен быть заменён платёжно подтверждённым контрактом, включая фактическую корректную обработку онлайн оплаты и фискализации. Старый QR POS plugin также имеет обязательный предохранитель и не принимает неоплаченный QR-заказ. До такого обновления `main` и production не менять.

## Контрольный список перед допуском к реальным платежам

- Test Payriff credentials and environment per test organization (никогда не размещать в браузере, чате и GitHub).
- Проверка merchant ID, AZN, суммы, reference и settled payment status через API Payriff.
- Тест отмены, отказа, двойного callback, переплаты/недоплаты, истечения срока и злоумышленного webhook.
- Поведение при POS offline, кухонном принтере offline, обновлении цены, стоп-листе и частичном возврате.
- Проверка без повторного POS-заказа, двойной кухонной печати и повторного списания денег.
- Отдельное юридическое/фискальное согласование обработки уже оплаченных онлайн заказов и возвратов в Азербайджане.
- Раздельные настройки Payriff и D1 tenant scopes; сначала тестовая касса и песочница.

**Для первой стадии с общим D1** `shared-test` остаётся диагностическим — только залы, столы и QR, без реальных денег и POS операций.
