# CHAIN — единые правила доступа и документов Smart Horeca

Статус: рабочий план; **не считать внедрённым целиком до приёмочного теста с реальным CHAIN**.

## Базовые инварианты

1. Каждый запрос имеет **Workspace / владелец данных** (storageUserId), **actor user ID** (кто выполнил действие), **роль/permissions** и **разрешённые Department ID**.
2. Клиентский cookie с выбранными ресторанами может только **сужать**, но не расширять разрешённый на сервере набор.
3. Каждый документ имеет владельца-подразделение. Если документ общий (центральный договор, закупка сети), доступ задаётся отдельным явным правом и набором подразделений.
4. Ключ согласования месячного табеля: `(storageUserId, month, contour, departmentId)`. Никогда не `A,B,C` и не ID конкретного менеджера.
5. Менеджер A подтверждает **только A**. Менеджер B — только B. HR с доступом к A/B/C видит все три документа и утверждает по одному. Все решения содержат actorId, время, комментарий и аудит.
6. При корректировке данных A устаревает утверждение A, а B/C остаются неизменными.
7. Сеть может показывать сводный Payroll, но **сводный просмотр не имеет побочных эффектов** (проводок, выплат, начислений). Для записи нужно выбрать конкретный ресторан и проверить его HR_APPROVED.
8. Текущий месяц нельзя финально подтвердить до конца месяца; события Face ID/исправления хранятся отдельно от решений HR.
9. Должностные и персональные правила рабочего времени настраиваются, но контроль персональных ограничений действует в серверных API.
10. Сотрудник, работавший в нескольких ресторанах, требует отдельного правила распределения часов/затрат: не допускать двойной выплаты по двум подразделениям.

## Проверяемые модули

| Модуль | Принцип CHAIN | Текущая готовность |
|---|---|---|
| Справочник сотрудников | по разрешённым ресторанам; HR сети видит несколько | базовые фильтры есть; все write API проверить |
| Face ID / учёт времени | события относятся к сотруднику и ресторану, оригинал RAW не изменяется | требуется аудит привязок и write API |
| Табель | каждый ресторан: свой документ и последовательность Manager → HR | реализуется PR #56, ждёт реального staging CHAIN |
| Дополнительные часы | менеджер подаёт по своему ресторану, HR утверждает, изменение сбрасывает только свой документ | основа в PR #56 |
| Payroll | отдельно по ресторану; центральная сводка только для просмотра | безопасный read-only режим CHAIN в PR #56; остальные financial endpoints проверить |
| Выплаты, авансы, Payroll-бухгалтерия | отдельные права и документы каждого ресторана; операции без дублирования | **не готово для CHAIN production**, необходим аудит |
| Закупки / заявки / RFQ / PO / приёмка | creator, Department ID, разрешённые ресторан/склад, индивидуальные согласования | в основном коде есть scopedByAccess; покрытие проверить |
| Склад, товары, списания | операция склада и подразделения; центральный просмотр при явном праве | проверить через серверный API |
| Кассы и кассовые смены | только разрешённые кассы/рестораны | проверить сквозные запросы |
| Финансы, P&L, налоги, аналитика | отдельный ресторан и консолидированная сводка, без утечек других ресторанов | частично реализовано, проверить endpoint-by-endpoint |
| AI Smart Horeca Assistant / документы | AI получает только серверно разрешённый scope; журнал аудита | проверить все источники данных |

## Приёмочный сценарий

Создать изолированный тестовый CHAIN A, B, C, Manager A, Manager B, Manager C, HR ALL, Payroll ALL, и при необходимости HR A+B (без C).

- Manager A видит A и не может получить B через API даже вручную.
- Каждый менеджер может подтвердить сентябрь A/B/C независимо.
- Общий HR видит три разных статуса, утверждает A после Manager A и B после Manager B, но не подтверждает за Manager C.
- Изменение одной корректировки в B переводит только B в черновик/«Изменён».
- HR A+B не видит C и не может передать C в POST.
- Текущий октябрь не утверждается ни через UI, ни через API.
- Payroll ALL отображает безопасную сводку без проводок; только выбранный A с HR_APPROVED может создать новые начисления A.
- При входе приглашённых используется общий storageUserId, а в аудите сохраняется настоящий actorId.
- Проверить повторно 503/CPU при табеле 316+ сотрудников и корректность Face ID.
- Проверить ограничения при смене cookie, Workspace и прямых URL, включая POST и кэш браузера.

## Очерёдность

1. PR #56 — базовые права и разделённые согласования, без production merge.
2. Аудит и миграция всех HR write/read endpoint: employee-profile/leaves/schedules, timeclock, payroll-adjustments, overtime-settlements, payroll-accounting, tax-settings, compensation.
3. Реальный тест CHAIN с минимум тремя ресторанами и ролями, затем решение о публикации.
4. Только после готовности HR — охват Procurement, Inventory, Cash, Finance/P&L, Reports и AI по единым инвариантам.
