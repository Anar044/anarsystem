# QR Menu → касса: внутренний этап до Payriff (октябрь 2026)

## Статус и запреты

- Реализована внутренняя регистрация QR-заказов в Cloudflare D1 и протокол задания для POS.
- **Исходники кассового плагина найдены:** `Anar044/Plagin` (полный C#-проект: `HorecaControl.cs`, `SocketIoConnector.cs`, `Core/Application/Services/OrderService.cs`, `.csproj`); также есть `Anar044/Plagin_and_kod`. Предыдущий вывод об отсутствии исходников был неверен: он относился только к репозиторию `Anar044/anar_posplagin` с DLL. Новый QR POS Bridge ещё не реализован в C# и не протестирован; нельзя считать заказ созданным в iikoFront до подтверждения плагина реальным POS Order ID.
- **Не включено**: онлайн-оплата Payriff, RRN Payriff, автоматическое списание/фискализация онлайн-оплаты, выбор получателя чаевых. Никакие статусы оплаченного заказа не ставятся через гостевой API.
- Пользователь может оформить заказ только при `orderingEnabled` **и свежем POS Bridge hello**; по умолчанию приём выключен. Если касса не подтверждала поддержку протокола последние пять минут, публичное создание заказа блокируется. Уже зарегистрированные заказы остаются в очереди.
- Временно единственная бизнес-схема оплаты: **PAY_AT_POS**. Фискализация производится действующей кассой после фактической оплаты в кассовом модуле и подтверждается новым POS Bridge. Это не «автооплата».

## Режимы QR

1. TABLE: администратор добавляет таблицу со своим случайным QR token. Публичная ссылка `/menu.html?id={public_slug}&table={table_key}`. Номер стола подставляется сервером из БД, не из гостевого POST. У стола может быть `pos_table_id`, его необходимо сопоставить с iikoFront.
2. FAST_FOOD: один общий `/menu.html?id={public_slug}` без table. Заказ получает общий UUID и короткий номер для показа гостю. Сотрудник кассы видит QR Order ID, который позже будет записан в POS external data.
3. Нажатие «Оформить заказ · оплатить на кассе» в корзине доступно только когда QR-заказы включены. Действующее визуальное оформление QR меню остаётся прежним, кроме дополнительного блока корзины.
4. Все цены берутся **из опубликованных данных D1**; передача цены с клиента игнорируется; количество, валюта AZN и доступность валидируются сервером. Предусмотрены UUID повторных запросов (idempotency) и ограничение частоты.

## Cloudflare Pages — окружение

- `DB`: существующий D1 binding с опубликованными `qr_menus`, `qr_dishes`, `qr_categories`.
- `QR_ORDER_RATE_SECRET`: обязательный случайный секрет для HMAC-подобного хеширования CF-Connecting-IP и предотвращения заказа десятков позиций в цикле. Не размещать в GitHub, скриптах или браузере. Без него админ не сможет включить гостевой заказ. IP хранится только как SHA-256 с секретом, id меню и id стола (либо FAST_FOOD). Ограничение: 8 заказов за 20 минут на стол+IP, 80 за 20 минут на IP в FAST_FOOD. Дополнительно нужен WAF/Turnstile при росте нагрузки: клиенты общего Wi-Fi могут иметь один IP.
- `PLUGIN_INGEST_TOKEN`: существующий серверный токен проверки кассового плагина; сервис проверяет реестр и departmentId.
- `QR_POS_BRIDGE_TOKEN`: дополнительный **отдельный** серверный секрет, необходим для запросов о выдаче и подтверждении POS-заказов. Без него POS Bridge выключен. По умолчанию нет никакой выдачи/закрытия.

Столы, настройки, заказы и события создаются внутри D1 автоматически. Для production рекомендуются контролируемые миграции и бэкап D1 перед выкладкой.

## POS Bridge — новый контракт для доработанного плагина

`POST /api/qr-menu/pos-bridge`, headers:
`X-Plugin-Token: <PLUGIN_INGEST_TOKEN>`, `X-QR-Bridge-Token: <QR_POS_BRIDGE_TOKEN>`, `Content-Type: application/json`.

Весь запрос включает `pluginId`, `departmentId`; Cloudflare проверяет зарегистрированную кассу на текущем SH backend, а ресторан должен совпадать с QR заказом. Из публичного меню POS Bridge недоступен.

0. После загрузки плагина и затем не реже одного раза в две минуты: `{"action":"hello","pluginId":"...","departmentId":"...","contractVersion":1,"canCreateOrder":true,"canAcknowledgeFiscal":true}` → `accepted:true`. Только зарегистрированный плагин с двумя секретами может подтвердить наличие нового контракта. Гостевое оформление нельзя включить без свежего hello (5 минут). Это программная готовность, **не** замена реального POS-тестирования.
1. `{"action":"pull","pluginId":"...","departmentId":"..."}` → `job` или `null`.
   - `job.externalOrderId` — **неизменный UUID** QR-заказа, используемый как idempotency key в плагине и/или `OrderExternalData`.
   - `job.items[]` — `productId` из iiko, `qty`, `unitMinor`, `lineMinor`; суммы в гяпиках. `job.mode`, `tableLabel`, `posTableId`, `totalMinor`, `currency`, `guestNote`.
   - `paymentMethod` = `PAY_AT_POS`, `onlinePaid=false`, `rrn=null`.
   - Lease 90 секунд; после истечения повторный `pull` может вернуть тот же заказ. **Доработанный плагин должен поискать существующий заказ по externalOrderId ДО создания нового**, чтобы не создавать дубликаты. Cloudflare lease сам по себе не обеспечивает exactly-once на кассе.
2. После успешного создания (но не закрытия):
`{"action":"ackCreated","pluginId":"...","departmentId":"...","externalOrderId":"...","posOrderId":"...","posOrderNumber":"..."}`
   → статус `POS_OPEN`.
3. При ошибке до подтверждения:
`{"action":"ackFailed","pluginId":"...","departmentId":"...","externalOrderId":"...","errorCode":"..."}`
   → статус `POS_FAILED`, ошибка остаётся у администратора.
   Если запрос к POS завершился по таймауту, а создание могло произойти, плагин должен проверить наличие заказа по `externalOrderId`; **не** слать `ackFailed` без проверки.
4. После оплаты и фактического фискального закрытия на кассе:
`{"action":"ackFiscalized","pluginId":"...","departmentId":"...","externalOrderId":"...","posOrderId":"...","receiptNumber":"...","fiscalReference":"...","paymentKind":"POS_CARD","rrn":"..."}`
   → `CLOSED` и `PAID_AT_POS`. Для `POS_CASH` RRN отсутствует. HTTP 200 из нашего QR API **не** является основанием для закрытия чека.

Порядок работы плагина: обработать очередь → проверить table/group/кассовую смену → найти/создать POS-заказ (правильная группа/секция, официант из кассы либо техпользователь, товары и модификаторы) → сохранить externalOrderId → ackCreated → направить на кухню по правилам кассы → дождаться реальной оплаты → использовать **уже работающую фискальную интеграцию** → ackFiscalized только после успешного завершения.

Документация API v7: https://iiko.github.io/front.api.sdk/v7/html/T_Resto_Front_Api_IOperationService.htm

## До начала работы с реальным POS

- Использовать C#-источники `Anar044/Plagin` как основу для нового pull/ack контракта. Перед сборкой сверить её с установленной DLL и версией iikoFront: `.csproj` в `Plagin` по умолчанию использует `Resto.Front.Api.V8` (8.7.6032), а совместимость с реальной кассой ещё не подтверждена.
- Определить: целевой терминал, точную секцию/кассу, идентификатор столов; обработку новых и распечатанных блюд; курсы, модификаторы, стоп-листы, количество гостей; принтеры кухни; согласование с открытым POS-заказом.
- Сравнивать итог на кассе с D1. Если отличаются цены/налоги/скидки, не пытаться автоматически закрыть: пометить конфликт и отправить на разбор.
- Убедиться, что в случае неработающей кассы заказ остаётся AWAITING_POS, а персонал не воспринимает его как переданный на кухню.
- Нужен отдельный тест для реальной кассы, смены, принтера, фискального чека и возврата. Без этого status POS_OPEN/CLOSED не следует считать проверенным функционалом.
- После Payriff: отдельный доверенный серверный webhook + status lookup + RRN + новые статусы `PAID_ONLINE_VERIFIED`; POS Bridge не должен считать будущую онлайн-оплату выполненной по данным гостя.
- Все страницы/режимы должны работать в AZ/RU/EN после подключения переводов: на данном этапе новый админ/гостевой интерфейс написан по-русски.

## Рекомендованные минимальные сценарии тестирования

- Стол 12 и Стол 13: разные QR; подменить `table` и `dishId`; проверить отсутствие доступа к чужому столику.
- Два разных ресторана одной CHAIN: невозможно видеть или получить заказ/QR чужого отделения.
- Два повтора одного `clientKey`: одна запись; изменённый состав с тем же ключом → HTTP 409.
- Вышедшее из продажи блюдо, невалидная цена, некорректное количество, множественные валюты.
- Касса отключена: заказ ждёт; после возвращения и включения `QR_POS_BRIDGE_TOKEN` может быть доставлен.
- Пропала связь после создания на POS, до `ackCreated`: повторный lease возвращает тот же `externalOrderId`, плагин находит существующий заказ.
- Клиент не может отправить `ackCreated` или `ackFiscalized` без обоих секретов и верной регистрации плагина.
- Закрытие без `receiptNumber` / `fiscalReference` либо с другим POS Order ID запрещено.
